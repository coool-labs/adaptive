## Biggest finding: virtual models

`pi.registerVirtualModel()` (T:1425, VM, VMD) was added in 0.99.0, where the changelog
calls it "experimental". The docs shipped with 1.5.0 do not call it experimental.

A virtual model is an entry in the model catalog, for example `adaptive/auto`. When the
user selects it, Pi calls the extension's
`route(request, ctx) → { model, thinkingLevel, state? }` before **every** provider
request. Each call carries `reason: "user" | "continuation" | "retry" | "direct"`
(VM:32, worked out at AS:474-483):

- **`user`:** the first request after a message the user wrote. This matches
  Adaptive's work-unit start, its admission boundary.
- **`continuation`:** later requests inside the run, such as after tool results. This
  matches "stay in-unit"; the router returns `previous` so the unit keeps its model.
- **`retry`:** Pi's automatic retry. The request includes
  `failed: { model, thinkingLevel, message }`, where `message` carries `stopReason` and
  `errorMessage`. **The router may return a different physical model, so the retry lands
  elsewhere** (VMD "Route requests": "A retry can also switch to another model"). That is
  exactly horizontal recovery within a tier.
- **`direct`:** requests outside the agent loop, such as compaction or extension calls.
  This matches Adaptive's auxiliary `RequestKind`.

Two more properties matter:

- Router `state` (JSON) is stored on the session branch as the custom entry
  `pi.virtual-model-state`. It follows forks and `/tree`, and survives compaction
  (AS:484-489, VMD "Keep routing state").
- The selection never changes; only each request's dispatch is routed. Adaptive therefore
  **never has to call `setModel`, `wait`, or `switch` to change models.** That removes
  the OpenCode `session.wait → switchModel → resume` sequence and the problem of telling
  our own switches apart from the user's.

This makes a Pi port structurally _simpler_ than the OpenCode adapter for routing. The
hard gaps are elsewhere: error metadata, the retry veto, parking, and global state.

## Loading, distribution and stability

- **Entry point [V]:** `export default function (pi: ExtensionAPI)`, sync or async
  (T:1541). The factory runs before `session_start`. Do not start timers, sockets or
  watchers in the factory; start them in `session_start` and clean up in
  `session_shutdown`, because factories also run in invocations that never start a
  session (EXT "Long-lived resources").
- **Loading [V]:** extensions are loaded through **jiti** (TypeScript without a build,
  `jiti@2.7.0` dependency).
- **Discovery [V]:**
  - `~/.pi/agent/extensions/*.ts|*/index.ts|*/package.json`
  - project-local `.pi/extensions/` (only after the project is trusted)
  - the `settings.json` entries `"packages": ["npm:@scope/pkg@x", "git:…"]` and
    `"extensions": [paths]`
- **Package manifest [V]:** `package.json` → `"pi": { "extensions": [...], "skills",
"prompts", "themes", "changelogPath" }`. `pi install` installs `dependencies` only.
  Host packages (`@earendil-works/*`, `typebox`) must **not** be listed as dependencies,
  because Pi maps them to its own copies.
- **Stability [V]:** no API stability or semver policy was found in the docs. **Post-1.0
  minor releases ship "Breaking Changes" that hit extensions:**
  - **1.2.0:** `before_agent_start` became a union; the session counts as busy during
    start, so `sendUserMessage` requires `deliverAs`.
  - **1.5.0:** tool validation moved to pi-schema.
  - **1.0.4:** a provider was renamed.
  - About 5 releases in 5 weeks. Expect churn; pin and test a version matrix, as with
    OpenCode.
  - Virtual models were labeled "experimental" when they shipped in 0.99.0. The 1.5.0
    docs no longer say so, but there is no explicit stability promise either.
- **Fail-open [V]:** handler errors are reported through `runner.emitError` and do not
  crash the run (EXT "Handler Composition"). This matches ADP-031. A throwing `route()`,
  however, **fails the request**, so the router must catch internally and fall back to
  `previous` or a default model to stay fail-open.

## Adapter sketch: `SupervisorOptions` against Pi

`SupervisorOptions` = `{ session, model, storage, clock, schedule, ledger }`. The adapter
also consumes hooks (`retry`, `context`, `model.request`, `http.response`,
`experimental.idle`, `prompt`), `session.execution.*` / `model.selected` events, tools,
commands, RPC, and `session.synthetic`.

**Maps cleanly:**

- `clock`: `Date.now`.
- `schedule`: an unref'd `setTimeout`, armed only after `session_start`.
- `model` (`ModelSource.transform` → candidate list): `ctx.modelRegistry.getAvailable()`,
  plus `find()` for pins. Thinking levels act as variants.
- The `prompt` hook (admission) becomes `route(reason:"user")`.
- The `context` / `model.request` hooks (request kind) become `route(reason)`:
  `continuation` (in-unit), `direct` (auxiliary).
- The `execution.started` / `succeeded` / `failed` / `interrupted` events become
  `agent_start` / `agent_settled{aborted}` plus the last assistant `stopReason`.
- `model.selected` becomes `model_select`. A non-virtual target means manual intent, so
  Adaptive yields.
- `experimental.idle` becomes `agent_settled`.
- The escalate and tier tools become `pi.registerTool` (TypeBox).
- The `/adaptive` command becomes `pi.registerCommand`, with `ctx.ui.select` / `confirm`
  dialogs.
- The TUI status chip becomes `ctx.ui.setStatus("adaptive", …)`, or just the built-in
  virtual-model footer.
- `session.synthetic({resume:false})` becomes `appendEntry` + `registerEntryRenderer`,
  or `ctx.ui.notify`.
- `SessionOpsSource.switchModel` / `wait` are **not needed**: routing replaces switching.
- Fail-closed to configured providers is enforced by `route()` itself.

**Needs workarounds:**

- **`retry` hook (veto plus redirect):**
  - Redirect becomes `route(reason:"retry")` returning a same-tier healthy model.
  - Veto becomes either a router throw with a non-retryable message, which ends the run
    **[I]**, or `ctx.abort()` during the backoff with a self-tag.
  - The backoff delay is Pi's (2s/4s/8s); Adaptive cannot shorten it.
  - The retry budget is Pi's `maxRetries`.
  - Pi will not retry quota or billing errors at all, so for those Adaptive must start
    the continuation itself.
- **Error classification:** no structured `status`, `type` or `retryAfterMs`. Write a Pi
  evidence reader over `errorMessage` (+ `diagnostics`). Reuse Pi's own exported
  `isRetryableAssistantError` semantics, and keep Adaptive's capability/infra split
  explicit.
- **`http.response` hook:** `after_provider_response` gives status and headers, but on
  most SDK providers only for _successful_ responses. That is fine for the quota-telemetry
  sensor (Codex fires for all) and poor for 429 Retry-After.
- **`storage` (global):** no host key-value store. Use files under `getAgentDir()` with
  locks, which must be cross-process safe because of subagent child processes. Per-session
  state goes into custom entries.
- **`ledger` (`ProcessLedger`, shared per process):** subagents are separate processes,
  so shared health moves to the file store. The ledger shrinks to a cache.
- **`session.prompt` (continuation after park):** `sendMessage(custom, {triggerTurn:true})`
  adds one small user-role message to context. Durable parking is re-armed on
  `session_start`. The **[I]** alternative for short waits is an async `route()` that
  awaits the reset.

**Impossible or absent (design must change, not just the adapter):**

- **A true retry veto that leaves the run alive and parked** has no host primitive. Every
  veto ends the run, either with an error message or an abort; the resume is then
  Adaptive-initiated.
- **"Continue from session state with no new message" after a delay.** Only
  `continue:true` at `turn_end` / `agent_before_settle` does that, and not after error
  outcomes. Delayed resumes always inject a message, which is a small privacy-neutral
  context cost, but still a change to the "never inject" stance for receipts (receipts
  themselves stay out).
- **Typed RPC to TUI and GUI** has no equivalent; Pi has no plugin RPC or web GUI mount.
  It is not needed, because the extension shares the TUI process, but `src/rpc/` and the
  GUI bundle do not port.
- **Seeing failed-response HTTP headers** on SDK-based providers is not exposed; only the
  error text is.
