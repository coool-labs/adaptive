## How pi-auto-model works (verified)

- **Virtual model.** It registers `pi-auto-model/auto`, whose `streamSimple` is a proxy (`src/pi/stream-proxy.ts:319`). Routing runs once per agent run in `before_agent_start`, or on the first `context` event for extension-triggered runs (`extensions/auto-model.ts:647-672`). The resulting ranked target list is stored in `pendingStreams` per session and reused for every `streamSimple` call in that run's tool loop (`:1144-1165`).
- **Task analysis is keyword/regex.** `src/task/local-analyzer.ts:10-22` holds 11 regexes (English and Chinese), for example `debug: /\b(debug|bug|error|exception|stack trace|fix)\b|调试|报错|异常|修复/i`. They feed hand-weighted scores for complexity, demand, risk and confidence. Confidence is `0.35 + min(kinds·0.18, 0.55) + (trace ? 0.1 : 0)` (`:104`).
- **LLM classifier.** It is **off by default** (`src/config/defaults.ts:91`: `classifier: { enabled: false, confidenceThreshold: 0.5, timeoutMs: 400 }`). When enabled, it fires when `confidence < threshold` (`src/task/classifier.ts:8-10`). With the default 0.5 threshold, the confidence formula makes it fire exactly when **no keyword regex matched**: 0.35, or 0.45 with a stack trace. It sends the first 1,200 characters of the prompt to the user's cheapest "light" candidate model, capped at 2 s and 128 tokens and charged against the budget (`classifier.ts:167-201`). It can set `minTier`, kinds, complexity, reasoning, vision and risk (`:104-156`). It never fires in preview (`extensions/auto-model.ts:763`).
- **Capability tiers are not user-declared.** They come from a hard-coded catalog (`src/models/capability.ts:76-89`, for example `anthropic/claude-sonnet: strong`) or from optional benchmark sources. Unknown models get tier `unknown`, which ranks 0, below `light` (`:111-124`).
- **Scoring is a weighted utility.** It combines quality, cost, stickiness, latency, reliability, quota, pool, preference and cache adjustment (`src/routing/route-planner.ts:355-399`). `rankedTargets` is **every eligible model sorted by utility, across tiers** (`:441-505`).
- **Routing precedence.** Session pin (`/auto-model pin`) > first-prompt prefix pin > config rules/scenarios > utility scoring. A budget `downgrade` can then swap in a cheaper plan (`extensions/auto-model.ts:1008-1109`). Nothing ever defers to Pi's own choice: an active session always picks a model or blocks.

## The specific questions

1. **Selection.** Keyword/regex analysis always runs (English and Chinese), then weighted utility scoring over catalog tiers. The LLM classifier is opt-in and fires only when confidence is below 0.5, which in practice means zero keyword matches. Verified.
2. **Silent cross-tier failover: yes.** In-request failover walks a utility list that spans tiers, and cross-task failover picks the next unattempted ranked target. When every candidate is rate-limited: quota-cooldown providers are still used if nothing else remains, and if every circuit is open the request errors with "Request blocked". There is **no park or wait**, and no automatic resume. It may also move _up_ a tier, because the in-request list includes stronger models when they rank next.
3. **The "2 tool errors → strongest" path.** The README wording is looser than the code. The code requires two **consecutive `execution`-class errors from the same tool**. Environment failures (`ENOENT`, `EACCES`, network) and failing tests (`validation`) _reset_ the counter (`extensions/auto-model.ts:1666`; `tool-failure.ts:7-10`). So it does **not** treat infra failures as capability failures. It _is_ a heuristic capability signal (regex over tool output), it is unstructured, and it switches model **mid-run**. Provider 429/5xx errors never trigger it.
4. **Breaker.** Single probe in-process (verified). A 429 trips it on the first occurrence. The breaker is not persisted. Provider-level `Retry-After`/`x-ratelimit-reset` is parsed (`src/quota/uvi.ts:124-162`) into `lastRetryAt`, which **is** persisted (next item) and feeds a soft provider "cooldown" quota status.
5. **Mid-stream.** Safe. After the first text or tool-call delta it never fails over or replays. A hang after output is ended only by the optional `requestTimeoutMs`, as an error.
6. **Abort and auth.** User abort stops at once, with no failover and no health penalty. Auth, 404 and other 4xx errors are not retried. 402 is treated as a non-retryable client error.
7. **Manual selection.** A concrete pick in `/model` suspends auto for the session until the user re-selects `pi-auto-model/auto`. Session-start re-selection of auto, first-prompt-only prefix pins, and floor-not-tier semantics are the caveats.
8. **Loops.** All bounded (see table).
9. **Observe, quota, persistence.** There is a shadow mode that interferes, and a pure preview command. Quota-reset awareness comes from `Retry-After`, `x-ratelimit-reset(-after)` and provider rate-limit headers (`src/quota/adapters.ts`). Persisted to `~/.pi/agent/auto-model/` with a cross-process file lock: `metrics.json` (including per-provider `lastRetryAt`, `src/metrics/route-metrics.ts:250-262, 421-440`), `budget.json`, `quality.json`, `prices.json` and `events.jsonl`. **In memory only:** circuit state, pins, activation, pending plans and failed-route memory (`src/pi/runtime-store.ts:20`). No work is parked.

### Suspected defect (static reading only, not run)

After an in-request failover exhausts `maxAttempts` with retryable errors, `onAttemptSettled` leaves `state.lastFailedRoute` holding 3 attempted IDs (`extensions/auto-model.ts:442-448`). `settleActiveTask` clears it only when `!resultRecorded`, but the proxy always sets `resultRecorded = true` (`:476, 1506-1508`). The next user prompt then sees `attemptedTargetIds.length >= maxAttempts` and returns "failover budget exhausted … Request blocked" _before_ the only other reset at `:1186` (`:894-908`). The blocked task has no `routeTargetId`, so settling it does not clear the field either. The likely result is that **every later prompt in the session is blocked** until the user toggles models. Running the shipped tests (not in the tarball) or a fake-provider repro would confirm or refute this.

## What is genuinely uncovered in the Pi ecosystem

Verified gaps, none of which any of the five packages covers:

- **Durable park and auto-resume after a quota reset.** Every package either errors, keeps the failing model, or replays. pi-gateway and pi-auto-model persist reset times but never wake the session.
- **Structured, auditable escalation.** No escalation tool, no reason + evidence schema, no reviewer or verification hook. pi-auto-model's regex-on-tool-output trigger is the only escalation found, and it switches mid-run.
- **Tier integrity together with no classifier.** pi-shift-router has tier integrity but an LLM judge. pi-gateway has user-declared tiers but no capability routing at all. pi-auto-model and pi-auto-router have neither.
- **429 kept out of breaker trips**, with single-probe half-open shared **across processes**. pi-auto-model has single-probe in-process only, and trips on the first 429.
- **An observe mode that cannot change outcomes.** pi-auto-model's shadow still fails over. pi-auto-model's `/auto-model plan` is the closest thing to it, as a one-shot preview.
- **402 / quota exhaustion as provider-wide capacity loss** feeding within-tier rotation. pi-auto-model treats 402 as terminal. pi-gateway's reset schedules come closest.
- **Restoring the preferred model strictly at safe boundaries**, with mid-run switches ruled out. pi-auto-model and pi-auto-router both fail over per HTTP call inside the tool loop.

What _is_ already well covered in Pi, and should be reused or not competed on: pre-output same-request failover through a virtual `streamSimple` provider (pi-auto-model's proxy is careful and good), compatibility gating, thinking-block stripping across APIs, per-attempt budget reservation, and header-based quota observation.
