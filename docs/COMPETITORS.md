# Competitors and positioning

Research date: 2026-11-03. Sources: each project's README or npm page, read directly unless marked otherwise. Nothing here was tested by running the other plugins. Re-check before quoting numbers or claiming a gap.

## The category already exists

OpenCode has many "switch model on rate limit" plugins. "Fallback on quota" is not a differentiator, and posts must not present it as one. Plain fallback is table stakes.

The closest competitor is `opencode-runtime-fallback`. It already continues from session state, recovers to the primary after a cooldown, and recognises some subscription-style messages. Do not describe Adaptive as the first to do these.

## What Adaptive does that the read READMEs do not

Each item is something I can back with a requirement and an automated test in this repo. "Not in the README" means the README I read does not mention it. It does not mean the plugin cannot do it.

1. **Capability and availability are separate.** Outages, limits and timeouts only move work within the same tier. A stronger tier is used only on structured evidence: explicit request, reviewer rejection, failed verification, repeated structured failure, or an explicit blocker, with a finite per-task budget. The fallback plugins read treat every failure as "next model in the list".
2. **Tiers, not one list.** quick / standard / advanced, each with its own ordered resources. No hidden borrowing across tiers: if a tier is exhausted, work parks and resumes, rather than silently landing on a different class of model.
3. **Quarantine at the narrowest justified scope.** Provider, account, model or variant, depending on the evidence. A shared subscription limit ("session", "usage", "weekly" limit, out of credits) blocks the whole provider. A model-specific limit blocks only that model. The same model name on another configured provider stays usable (ADP-006, ADP-007). `opencode-runtime-fallback` has a provider-level skip for workspace rate limits; the scope rules and the shared-versus-model split are not in its README.
4. **Circuit breaker with a single half-open probe.** One probe request tests a recovering resource. Concurrent callers do not stampede it. 429s do not count toward breaker trips. `azumag` has a breaker; the single-probe rule is not in its README.
5. **Durable state.** Health, quarantines, settings, per-session modes and parked work survive restarts. `opencode-runtime-fallback` states that its background delivery has no durable ledger across cold restarts.
6. **Never replays the original prompt.** Recovery continues from session and workspace state with a fixed continuation prompt (ADP-023). `azumag`, `Aldo-f` and `@ichisay` describe resending the last user message.
7. **Safe-boundary routing.** Routing happens at work-unit start or end. A steering message during active work does not switch the model, and a productive model is never pulled away mid-work.
8. **Observe mode and receipts.** Observe mode runs the same scheduler as active mode but applies nothing. Every decision leaves a bounded receipt with the reason and the resources skipped.
9. **Manual intent wins** while the picked model is usable, and yields only when it is health-blocked (ADP-028).
10. **Verification depth.** 100% coverage gate, real-host end-to-end suites against OpenCode itself (runtime, web, terminal UI), and packed-plugin tests across three host versions.

## Where competitors are ahead or equal

- `opencode-runtime-fallback`: per-agent chains, time-to-first-token timeout (aborts a hung model), compaction fallback, foreground and background subagent handling, toasts and desktop notifications. Adaptive has none of the TTFT timeout, per-agent chain override or compaction fallback.
- `azumag`: backoff strategies with jitter, metrics export, error-pattern learning, hot reload. Adaptive has none of these.
- Anyone with API keys behind a router or proxy already has fallback outside OpenCode.
- Adaptive's classifier has only been checked against real Claude and ChatGPT limit wording. Others are matched by generic quota phrases.

## Messaging rules

- Never say "no other plugin does this" or "the first". It is false and easy to disprove in the comments.
- Lead with what is actually different: availability never changes capability, tiers with narrow-scope quarantine, durable state, no prompt replay, observe mode.
- Describe the subscription-limit pain as the motivating case, not as the unique feature.
- Credit `opencode-runtime-fallback` and `azumag` by name. A visible comparison reads as honest and pre-empts the "this already exists" reply.

## Open checks before publishing claims

- Done, partly: the built-in `RETRYABLE_ERROR_PATTERNS` of `opencode-runtime-fallback` (cloned 2026-11-03, 15 patterns in `constants.ts`) were run against Claude subscription wording. "You've hit your session limit · resets 6:10pm", "You've hit your weekly limit" and "You've hit your usage limit" do not match any pattern. Only the exact phrase "usage limit has been reached" matches. This tests the pattern list only. It did not run the plugin inside OpenCode, and users can add their own `retryable_error_patterns`. Treat it as "not covered by default", not "cannot work".
- Done, same method, 2026-11-03: default pattern lists of the other fallback plugins were read from source (or the published npm `dist`) and run against the same four messages (`/tmp/competitor/check2.mjs`). Case-insensitive substring match, as each plugin does.
  - `liamvinberg`, `Aldo-f`, `azumag` (general and vendor lists) and `@ichisay` (rate-limit and quota lists): "You've hit your usage limit" and "Claude usage limit reached" match through the substring "usage limit". "You've hit your session limit · resets …" and "You've hit your weekly limit" do not match.
  - `lichti`: none of the four match on text (429, too many requests, rate limit, quota exceeded, resource exhausted). It relies on a structured 429 status, so it only helps if the host reports one.
  - `azumag` ignores messages containing "not your plan limits" and "draw from your extra usage" by default.
  - All of these allow custom patterns, and a host-reported 429 status would trigger most of them. The test covers default text patterns only, not the plugins running inside OpenCode.
- Not fallback plugins, confirmed from README: `@fazaboa/opencode-auto-continue` continues responses cut off by the output-token cap. `@dracondev/opencode-auto-continue` continues stalled sessions and compacts on token-limit errors. `@vymalo/opencode-ratelimit` waits on gateway headers and has no model switching. `@crystalfluxay/opencode-rate-limiter` is proactive TPM/RPM limiting with a status-code rule table and a fallback list.
