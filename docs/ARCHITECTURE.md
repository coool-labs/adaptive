# Architecture

## Ownership

Adaptive supervises execution; the host remains the agent runtime. It does not
plan tasks, replay prompts, classify work with an LLM, or silently borrow tiers.

| Workspace           | Responsibility                                                                  | Published                  |
| ------------------- | ------------------------------------------------------------------------------- | -------------------------- |
| `packages/core`     | Pure routing, health, state parsers/stores, recovery policy, shared dialog flow | No; bundled into plugins   |
| `packages/testkit`  | Deterministic loopback provider and scripted scenarios                          | No                         |
| `packages/opencode` | OpenCode lifecycle, retry veto, RPC, TUI and GUI bindings                       | `@coool/opencode-adaptive` |
| `packages/pi`       | Planned Pi virtual-model, lifecycle, file-storage and native UI bindings        | Not released yet           |
| `scripts`           | Verification, packaging, traceability and coordinated releases                  | No                         |

Private source exports are category subpaths, not a platform abstraction layer.
The plugins bundle core code and declarations; no published dependency field may
reference a private workspace. Source maps retain embedded original sources.
Pack validation checks every export target and executable/declaration artifact.

## Boundaries

Core and testkit do not import host SDKs or either plugin. ESLint enforces this
for production and test code. Clock, inventory, storage and effects are injected;
the scheduler remains a pure function of settings, inventory, health, capacity,
request context and time. Observe and active call this same scheduler.

Core owns policy, not the lifecycle adapter. OpenCode's episode tracker and
supervisor stay in its plugin. Pi needs its own tracker because ordinary tool
continuations and owned post-settle recovery have different host semantics.
Shared dialog flow accepts `HostCopy`: entire host-specific explanations are
injected, not generated by replacing a product name in misleading text.

The host applies effects at safe boundaries. In-unit tool continuations remain
on their resource. Infrastructure failures recover within the required tier;
only a failed unit plus structured capability evidence can justify escalation.
Durable recovery continues from session/workspace state, never the original prompt.

## State and concurrency

Core defines bounded, versioned data and defensive readers. Plugins provide
storage. OpenCode uses its host storage interfaces. Pi's planned file binding
must lock and atomically update cross-process state, including probe leases and
wake claims; an in-memory mutex is insufficient. Secrets never enter receipts,
logs, state or UI payloads. Missing evidence is not inferred telemetry.

## Verification and releases

`npm test` runs all unit projects without hosts. Each workspace and the tested
tooling policy have their own 100% coverage gate. `npm run check -- --all` runs
fast gates; `npm run verify -- --all` additionally builds, inspects tarballs and
runs packed-host/runtime/UI tests and applicable requirements traceability.

`npm run release:status` finds changes since each plugin's own tag, including
shared-core/testkit commits. `npm run release` verifies bumped artifacts, then
commits, tags and publishes selected packages. Preparation failure restores only
its own uncommitted edits. After a release commit, recovery uses `--resume` and
checks the registry before publishing missing versions. Merely preparing a
release does not authorize running the publishing command.
